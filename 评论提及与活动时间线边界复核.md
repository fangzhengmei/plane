# Issue 活动时间线边界复核报告

## 复核概述

本报告从代码实事出发，对 Plane 仓库 Issue 活动时间线实现的三个边界问题进行逐行复核：

1. 默认分支 `chain` 后 `instance["created_at"]` 的运行时类型安全性
2. 前端 service 层 `issue-property` / `issue-comment` 的实际参数传递与 store 合并映射
3. `IssueComment.access` 字段在时间线查询中的区分情况

---

## 一、默认分支 `chain` 后 `instance["created_at"]` 的运行时类型安全性

### 1.1 问题代码

**文件**：`apps/api/plane/app/views/issue/activity.py:81-84`

```python
result_list = sorted(
    chain(issue_activities, issue_comments),
    key=lambda instance: instance["created_at"],
)
```

### 1.2 逐行类型追踪

**变量 `issue_activities`（第 35-46 行）**：

```python
issue_activities = (
    IssueActivity.objects.filter(issue_id=issue_id)     # 返回 QuerySet
    .filter(...)                                          # 仍为 QuerySet
    .filter(**filters)                                    # 仍为 QuerySet
    .select_related("actor", "workspace", "issue", "project")  # 仍为 QuerySet
).order_by("created_at")                                  # 仍为 QuerySet
```

类型结论：`issue_activities` 是 `QuerySet[IssueActivity]`，迭代时产出 **Django Model 实例**。

**变量 `issue_comments`（第 47-64 行）**：

```python
issue_comments = (
    IssueComment.objects.filter(issue_id=issue_id)      # 返回 QuerySet
    .filter(...)                                          # 仍为 QuerySet
    .filter(**filters)                                    # 仍为 QuerySet
    .order_by("created_at")                               # 仍为 QuerySet
    .select_related(...)                                  # 仍为 QuerySet
    .prefetch_related(...)                                # 仍为 QuerySet
)
```

类型结论：`issue_comments` 是 `QuerySet[IssueComment]`，迭代时产出 **Django Model 实例**。

### 1.3 对比 `issue-property` / `issue-comment` 分支

**第 66-75 行**（`issue-property` 分支）：
```python
if request.GET.get("activity_type", None) == "issue-property":
    issue_activities = IssueActivitySerializer(issue_activities, many=True).data
    #                                   ^^^^^^^^^^^^ 序列化为 ReturnList[dict]
    return Response(issue_activities, status=status.HTTP_200_OK)
```

**第 77-79 行**（`issue-comment` 分支）：
```python
if request.GET.get("activity_type", None) == "issue-comment":
    issue_comments = IssueCommentSerializer(issue_comments, many=True).data
    #                              ^^^^^^^^^^^^ 序列化为 ReturnList[dict]
    return Response(issue_comments, status=status.HTTP_200_OK)
```

**关键差异**：两个显式分支都调用了 `.data` 将 QuerySet 序列化为字典列表，而默认分支**未调用任何序列化器**。

### 1.4 运行时行为分析

`itertools.chain(issue_activities, issue_comments)` 的行为：
1. `chain` 不触发 Django QuerySet 求值，返回一个迭代器
2. `sorted()` 消费迭代器时，触发两个 QuerySet 的数据库查询
3. 迭代器产出的每个元素是 **Django Model 实例**（`IssueActivity` 或 `IssueComment`）
4. `lambda instance: instance["created_at"]` 对 Model 实例执行字典式访问

**Django Model 实例是否支持 `instance["created_at"]`？**

Django Model 的 `__getitem__` 方法（定义在 `django.db.models.Model`）的行为：
- Django Model **没有**实现 `__getitem__` 方法
- 对 Model 实例执行 `instance["created_at"]` 会触发 `TypeError: 'IssueActivity' object is not subscriptable`

### 1.5 触发条件

| 条件 | 说明 |
|-----|------|
| 请求参数 | 不携带 `activity_type` 参数，或 `activity_type` 不等于 `"issue-property"` / `"issue-comment"` |
| 请求路径 | `GET /api/v1/workspaces/{slug}/projects/{project_id}/issues/{issue_id}/history/` |
| 数据条件 | 该 Issue 下同时存在 IssueActivity 和 IssueComment 记录（若只有一类则 `chain` 后排序也可能触发） |
| 触发概率 | **100%**：只要请求不携带 `activity_type` 参数，且存在任何活动或评论记录 |

### 1.6 风险级别

🔴 **严重**：该分支在运行时**必然抛出 `TypeError`**，导致 500 错误。

**结论**：前端 Web App 的两个 service **始终携带 `activity_type` 参数**，因此默认分支在前端正常使用中**不会被触发**。但默认分支仍是一个**死代码 Bug**：
1. 若有第三方 API 客户端不携带 `activity_type` 参数，会触发 500 错误
2. API 端点没有文档说明 `activity_type` 为必填参数
3. 代码逻辑暗示默认分支应正常工作（合并返回），但实际不可用

### 1.8 修复建议

```python
# 方案 A：默认分支先序列化再排序
result_list = sorted(
    chain(
        IssueActivitySerializer(issue_activities, many=True).data,
        IssueCommentSerializer(issue_comments, many=True).data,
    ),
    key=lambda instance: instance["created_at"],
)

# 方案 B：Model 实例用属性访问排序，再由 Response 触发序列化
result_list = sorted(
    chain(issue_activities, issue_comments),
    key=lambda instance: instance.created_at,  # 属性访问而非字典访问
)
```

### 2.2 Store 合并映射（代码证据）

**文件**：`apps/web/ce/store/issue/issue-details/activity.store.ts:87-139`

```typescript
protected buildActivityAndCommentItems(issueId: string): TIssueActivityComment[] | undefined {
    const activityComments: TIssueActivityComment[] = [];
    const currentStore =
        this.serviceType === EIssueServiceType.EPICS
            ? this.store.issue.epicDetail
            : this.store.issue.issueDetail;

    // ========== 从 Activity Store 取活动 ID 列表 ==========
    const activities = this.getActivitiesByIssueId(issueId);
    // ========== 从 Comment Store 取评论 ID 列表 ==========
    const comments = currentStore.comment.getCommentsByIssueId(issueId);

    if (!activities || !comments) return undefined;

    // ========== 活动 → 统一结构 ==========
    activities.forEach((activityId) => {
        const activity = this.getActivityById(activityId);
        if (!activity) return;
        const type =
            activity.field === "state" ? EActivityFilterType.STATE :
            activity.field === "assignees" ? EActivityFilterType.ASSIGNEE :
            activity.field === null ? EActivityFilterType.DEFAULT :
            EActivityFilterType.ACTIVITY;
        activityComments.push({
            id: activity.id,
            activity_type: type,
            created_at: activity.created_at,
        });
    });

    // ========== 评论 → 统一结构 ==========
    comments.forEach((commentId) => {
        const comment = currentStore.comment.getCommentById(commentId);
        if (!comment) return;
        activityComments.push({
            id: comment.id,
            activity_type: EActivityFilterType.COMMENT,
            created_at: comment.created_at,
        });
    });

    return activityComments;
}
```

**事实**：
- Activity Store 和 Comment Store **分别独立拉取数据**（两个不同的 API 请求）
- 合并发生在前端 Store 的 `buildActivityAndCommentItems` 方法中
- 合并后的数据结构为 `TIssueActivityComment[]`，统一包含 `id`、`activity_type`、`created_at` 三个字段
- `activity_type` 映射由前端根据 `activity.field` 值在前端完成（后端不返回 `activity_type` 字段）

```typescript
public async fetchActivities(workspaceSlug, projectId, issueId, loaderType) {
    let props = {};
    const currentActivityIds = this.getActivitiesByIssueId(issueId);
    if (currentActivityIds && currentActivityIds.length > 0) {
        const currentActivity = this.getActivityById(currentActivityIds[currentActivityIds.length - 1]);
        if (currentActivity) props = { created_at__gt: currentActivity.created_at };
    }
    // ✅ 始终传 activity_type=issue-property
    const activities = await this.issueActivityService.getIssueActivities(workspaceSlug, projectId, issueId, props);
    runInAction(() => {
        update(this.activities, issueId, (currentActivityIds) => {
            return uniq(concat(currentActivityIds, activityIds));  // 增量合并
        });
        activities.forEach((activity) => {
            set(this.activityMap, activity.id, activity);
        });
    });
}
```

| 职责 | 后端 API | 前端 Service | 前端 Store | 前端 UI |

| 决定请求 `activity_type` | ❌ | ✅ 硬编码 `issue-property` / `issue-comment` | ❌ | ❌ |

### 2.5 关键发现

1. **前端从不调用默认分支**：两个 Service 始终携带 `activity_type` 参数，后端默认分支（第 81-84 行）在前端正常使用中不会被触发
2. **合并职责在前端**：后端只分别返回 `IssueActivity` 和 `IssueComment` 的序列化数据，合并排序完全由前端 Store 承担
3. **两个 Service 调用同一个 URL**：`issue_activity.service.ts` 和 `issue_comment.service.ts` 都请求 `/history/` 端点，仅通过 `activity_type` 参数区分返回内容
4. **增量加载独立计算**：Activity Store 和 Comment Store 各自独立计算 `created_at__gt` 参数，互不影响

## 三、`IssueComment.access` 字段在时间线查询中的区分情况

### 3.1 `access` 字段定义

**文件**：`apps/api/plane/db/models/issue.py:467-471`

```python
class IssueComment(ChangeTrackerMixin, ProjectBaseModel):
    ...
    access = models.CharField(
        choices=(("INTERNAL", "INTERNAL"), ("EXTERNAL", "EXTERNAL")),
```

**字段语义**：
- `INTERNAL`：内部评论，仅项目成员可见（默认值）
- `EXTERNAL`：外部评论，可通过公开部署面板（DeployBoard）查看

#### 公开部署面板（Space API）中的 `access` 过滤

**文件**：`apps/api/plane/space/views/issue.py:228-252`

```python
class IssueCommentPublicViewSet(BaseViewSet):
    def get_queryset(self):
        project_deploy_board = DeployBoard.objects.get(anchor=self.kwargs.get("anchor"), entity_name="project")
        if project_deploy_board.is_comments_enabled:
            return (
                super().get_queryset()
                .filter(workspace_id=project_deploy_board.workspace_id)
                .filter(issue_id=self.kwargs.get("issue_id"))
                .filter(access="EXTERNAL")  # ✅ 唯一过滤 access 的地方
```

**事实**：**仅**在公开部署面板（Space）的 `IssueCommentPublicViewSet` 中对 `access` 做了 `.filter(access="EXTERNAL")` 过滤。

### 3.3 完整对比

| 查询场景 | 文件 | 是否过滤 `access` | 可见范围 |
|---------|------|-----------------|---------|
| 时间线 API（activity 端点） | `app/views/issue/activity.py:47-64` | ❌ 不过滤 | INTERNAL + EXTERNAL 全部可见 |
| 评论 CRUD API（comment 端点） | `app/views/issue/comment.py:35-61` | ❌ 不过滤 | INTERNAL + EXTERNAL 全部可见 |
| 公开部署面板（Space） | `space/views/issue.py:228-252` | ✅ `.filter(access="EXTERNAL")` | 仅 EXTERNAL 可见 |

### 3.4 `access` 字段的写入路径

| 路径 | `access` 值 | 文件位置 |
|-----|-----------|---------|
| 内部评论创建 | `"INTERNAL"`（默认） | `app/views/issue/comment.py:84` `serializer.save(project_id=project_id, issue_id=issue_id, actor=request.user)` |
| 外部评论创建 | `"EXTERNAL"` | `space/views/issue.py:268-272` `serializer.save(project_id=..., access="EXTERNAL")` |

### 3.5 对权限和可见性的影响

#### 当前行为

1. **内部用户（项目成员）**：通过 Activity API 或 Comment API 查询时间线时，**同时看到 INTERNAL 和 EXTERNAL 评论**，无法区分两类评论
2. **外部用户（部署面板访客）**：通过 Space API 查询时，**仅看到 EXTERNAL 评论**，INTERNAL 评论被过滤

#### 潜在问题

| 问题 | 影响级别 | 说明 |
|-----|---------|------|
| 内部用户无法区分内部/外部评论 | 🟡 中等 | 前端没有 UI 标识区分，用户不知道某条评论对外部访客可见 |
| 内部用户无法筛选只看内部/外部评论 | 🟡 中等 | 后端未提供 `access` 筛选参数，前端无对应过滤功能 |
| EXTERNAL 评论在内部时间线中无特殊标识 | 🟡 中等 | 可能导致内部用户意外发布敏感信息到外部可见评论 |
| 内部评论不会出现在部署面板 | ✅ 符合预期 | Space API 正确过滤了 `access="EXTERNAL"` |

### 4.2 FIND-001 详细分析

**Bug 代码**：
```python
result_list = sorted(
    chain(issue_activities, issue_comments),  # 合并两个 QuerySet
    key=lambda instance: instance["created_at"],  # ❌ Model 实例不支持字典访问
)
```

**运行时类型链**：
```
issue_activities: QuerySet[IssueActivity]  →  迭代产出 IssueActivity Model 实例
issue_comments:   QuerySet[IssueComment]   →  迭代产出 IssueComment Model 实例
chain(...):       itertools.chain          →  迭代产出混合 Model 实例
sorted(..., key=lambda instance: instance["created_at"])
                                             ↑ TypeError: Model 不支持 __getitem__
```

**触发条件**：
- 请求 `GET /api/v1/workspaces/{slug}/projects/{project_id}/issues/{issue_id}/history/`
- **不携带** `activity_type` 参数

**前端规避**：
- `IssueActivityService` 始终携带 `activity_type=issue-property`
- `IssueCommentService` 始终携带 `activity_type=issue-comment`
- 因此前端正常使用**不会触发此 Bug**

**影响范围**：
- 前端 Web App：❌ 不受影响
- 第三方 API 客户端：✅ 可能受影响
- API 文档/测试：✅ 应标注 `activity_type` 为必要参数
